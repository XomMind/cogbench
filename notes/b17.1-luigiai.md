# LuigiAI in Cogmind Beta 17.1 — reverse engineering notes

**Research notebook:** findings below are chronological, and later rounds can
supersede earlier conclusions. For everyday use, start with [the main guide](../README.md),
[setup](../SETUP.md), or [OBS](../OBS.md). The original setup experiments are in
[the historical setup log](setup-history.md).

Target: `COGMIND.exe`, Beta 17.1, 9,347,072 bytes, PE32 i386, ImageBase `0x00400000`.
`DllCharacteristics = 0x8100` — no `DYNAMIC_BASE`, and the image has **no `.reloc` section**,
so it cannot be relocated and every VA below is literal at runtime.

Build is MSVC 2010 at `/Od` — `initialize()` reloads `this` from `-0x4(%ebp)` before every
field store — which is why this is tractable without symbols.

## Status

The `-luigiAi` / `-luigiAiTest` switch strings and the twelve `luigiAi/` path literals that
Beta 14 carries (file offsets `0x710adc`–`0x710c34`, switch at `0x72b3a0`) are **not** present
as plaintext in Beta 17 or 17.1. The **code is fully intact**. Missing strings are not evidence
of missing code; verify with numeric immediates instead.

## Globals

| Symbol | VA | Notes |
|---|---|---|
| `luigiAiActive` | `0x00CEFB3E` | `bool`. 17 refs in `.text`. Gates the entire subsystem. |
| `luigiAiTest` (probable) | `0x00CEFB36` | `bool`. 2 refs. |
| `luigiAi` | `0x00CEBFFC` | The `LuigiAi` instance. 7 refs. |
| `luigiAi.mapData` | `0x00CEC018` | `= 0xCEBFFC + 0x1C`; read directly by the guards. |

Both flag bytes and the struct live at RVAs past the end of `.data`'s raw data
(raw covers RVA `< 0x8EAC00`; the flag is at RVA `0x8EFB3E`) — i.e. in the zero-fill tail.
They do not exist in the file on disk and **cannot be patched there**. They must be written
into the loaded image.

## `LuigiAi::loadMap()` @ `0x00777BE0` — decoded

```c
this->mapWidth  = call_0x45D0F0(obj_0xCFD44C);        // map width
this->mapHeight = call_0x9B8330(obj_0xCFD44C);        // map height
this->locationDepth = -(*(int*)(call_0x9B7B50(obj_0xD1E888) + 0x08));
this->locationMap   =  *(int*)(call_0x9B7B50(obj_0xD1E888) + 0x04);

if (this->mapData) this->cleanup();

count = this->mapWidth * this->mapHeight;
mem   = operator new[](count * 0x1C + 4);             // 0xA0430A
*(int*)mem = count;                                   // array cookie
vector_ctor_iterator(mem+4, 0x1C, count, LuigiTile::ctor, LuigiTile::dtor);  // 0xAA0D4F
this->mapData = mem + 4;
```

### Facts extracted

* **`sizeof(LuigiTile) == 0x1C == 28 bytes.`** Matches
  `lastAction(4) + lastFov(4) + cell(4) + doorOpen(1→4 padded) + prop(4) + entity(4) + item(4)`.
  Any Rust mirror must be exactly 28 bytes or every tile after the first is garbage.
* **`0x00CFD44C` is the internal map / BattleScape object.** Width getter `0x0045D0F0`,
  height getter `0x009B8330`. This is the handle for a privileged (FOV-independent)
  observation channel — see below.
* **`0x00D1E888` is the location/world object.** `+0x04` = map type, `+0x08` = depth
  (negated on the way into `LuigiAi`).
* `loadMap()` **only allocates and default-constructs.** It never fills tile content.
  Tiles are populated by `updateLuigiAiMapTile(Cell*, bool includeItem)`, which is where
  the FOV gating lives. That function is among the remaining `luigiAiActive` xrefs:
  `0x004B12F9  0x0064EC11  0x007268FF  0x00726A54  0x00774D0F  0x0083870A
   0x008657C9  0x0090C113  0x009391E8` (+5 more).

## Privileged observation channel — do NOT patch FOV

Widening FOV changes enemy activation and behaviour, i.e. the environment's *dynamics*,
not just its observability. A policy trained against that is training against a different game.

The FOV-independent route with zero behavioural change is `0x00CFD44C`: it is the object the
game itself queries for map dimensions, so it owns the internal `Cell` array. Walking it gives
full ground truth while the game runs unmodified. Intended use is a **privileged critic**
channel (asymmetric actor-critic): full state to the critic during training, FOV-limited
observations to the actor, and evaluation always unpatched.

## Not yet resolved

* Which of `0x00CEFB3E` / `0x00CEFB36` is `active` vs `test` — inferred from the 17-vs-2
  reference split and guard position, not confirmed by running.
* Whether the ID-table dumpers (`cellID.txt` etc.) still work. They are gated on the same
  flag but their path literals are gone from plaintext. If the strings are encrypted at rest
  and decrypted at runtime, they will simply work once the flag is set.
* `sizeof(LuigiItem)` — the public `luigiai.h` has `{itemID; int integrity; bool equipped;}`
  (12 bytes with padding); `StatMind/AGENT.md` records `equipped` being removed to fix
  b16 misalignment. Confirm from an allocation site before trusting inventory walks.
* Cell names are **composed at runtime**, not stored whole: the exe holds `EARTH`, `EARTH_EXC`,
  `GROUND`, `TEMP_WALL`, `SEALED_DOOR`, `SHORTCUT_KNOWN`, `PHASEWALL_KNOWN` plus the prefixes
  `FLOOR_`, `WALL_`, `BARRIER_`, `SHORTCUT_`, `PHASEWALL_`, `DOOR_`, `STAIRS_` at `0x7EE660`.
  That is why searching for `FLOOR_SAN` finds nothing.

# Round 2: the map object, and what the flag does *not* buy you

## Correction: the per-tile mirror is stubbed out in 17.1

`updateLuigiAiMapTile(Cell*, bool)` is at **`0x009F2CE0`** in Beta 17.1, and its
entire body is:

```
9f2ce0: 55        pushl %ebp
9f2ce1: 8b ec     movl  %esp, %ebp
9f2ce3: 5d        popl  %ebp
9f2ce4: c3        retl
```

An empty function. The two callers iterate a rectangle and call it per cell
(`0x007268FC`, `0x00726A51`), guarded by `luigiAiActive` — but the callee does
nothing. **So setting `0x00CEFB3E` allocates `mapData` and never fills it: every
tile stays `NO_CELL`.** The one-byte patch is necessary but not sufficient.

The identification is solid: the same call site in Beta 14 reaches
`0x006E9280`, which has a full body that writes the LuigiTile fields (below).

### What the flag *does* still buy you in 17.1

Writers confirmed present:

| Field | Offset | Written by |
|---|---|---|
| `mapWidth` / `mapHeight` / `locationDepth` / `locationMap` | `+0x0C`…`+0x18` | `loadMap()` via `this` |
| `mapData` | `+0x1C` | `loadMap()` — allocated, never filled |
| `mapCursorIndex` | `+0x20` | `0x00774D53` / `0x00774D5B` |
| `player` | `+0x24` | `0x00865898` / `0x008658B6` |
| `machineHacking` | `+0x28` | 12 sites |

`actionReady` (`+0x08`) has **no absolute-address writers**. That does not prove
it is never written — a register-based writer would not show up in this scan —
but it needs confirming at runtime, because the whole action handshake depends
on it.

## The map object at `0x00CFD44C`

From `cellAt` (`0x009CF7D0`, thiscall, `retl $8`):

```c
Cell** cellAt(this, int x, int y) {
    int idx = x * this->[0x04] + y;
    return (Cell**)this->[0x08] + idx;
}
```

So the global at `0x00CFD44C` is:

| Member | VA | Type |
|---|---|---|
| `width` | `0x00CFD44C` | `int` |
| `height` | `0x00CFD450` | `int` |
| `cells` | `0x00CFD454` | `Cell**` — `width*height` pointers |

Accessors: width `0x0045D0F0` (`return this[0]`), height `0x009B8330`
(`return this[1]`).

**This array is the privileged channel.** It is the game's own live cell table,
complete regardless of FOV and regardless of `luigiAiActive`. Reading it needs no
patch and changes no behaviour — unlike widening FOV, which would alter enemy
activation and therefore the environment's dynamics.

## Index formula, confirmed by the game's own arithmetic

`0x00774D0C` computes `luigiAi.mapCursorIndex`:

```c
if (luigiAiActive) {
    Coord c;
    if (cursorOverMap(*(void**)0x00CEC054, &c))
        *(int*)0x00CEC01C = mapHeight() * c.x + c.y;
    else
        *(int*)0x00CEC01C = -1;
}
```

`height * x + y` — matching `luigiai.h`'s `access = x*mapHeight+y` and matching
`cellAt`. The column-major fix in the Rust reader is correct.

`0x00CEC054` holds the object answering "is the cursor over the map, and where"
(`0x00804EE0`, takes a `Coord*`, returns bool). That is the starting point for
the tile↔pixel mapping the mouse commands need.

## `sizeof(LuigiItem) == 12` — settled

From b14's `updateLuigiAiMapTile` (`0x006E9280`), the two allocations are:

```
6e935c: pushl $0x8    ; operator new -> stored to LuigiTile+0x10  (prop)
6e9407: pushl $0xc    ; operator new -> stored to LuigiTile+0x18  (item)
```

`+0x10` is `prop` and `+0x18` is `item`, so `sizeof(LuigiProp) == 8` and
**`sizeof(LuigiItem) == 12`**. The public `luigiai.h` — `{itemID; int integrity;
bool equipped;}` — is right, and `StatMind/AGENT.md`'s note about removing
`equipped` is wrong. `STATMIND_ITEM_STRIDE` should stay at its default of 12.

(Evidence is from b14. `sizeof(LuigiTile) == 0x1C` is identical in b14 and 17.1,
so the layout is stable across that span, but confirm once inventory reads
return plausible names.)

## LuigiTile field offsets, cross-checked

b14's mirror writes `+0x08` (cell), `+0x0C` (doorOpen), `+0x10` (prop),
`+0x18` (item), with stride `0x1C` — matching `luigiai.h` and matching the
`count * 0x1C + 4` allocation in 17.1's `loadMap()`.

## Consequences

Reading the game's `Cell**` directly is now the better primary path, not just the
privileged one:

* it does not depend on the stubbed mirror, so it works on 17.1 today;
* the same read serves both views — filter by the cell's own FOV state for the
  actor, leave it unfiltered for a critic;
* it is where sensor/radar visibility would live too, if it is modelled
  separately from FOV.

Remaining unknown: the `Cell` layout itself. b14's mirror reaches every field
through one-line accessors rather than raw offsets — `getCoord` `0x00457BC0`,
`getCellId` `0x0045A890`, `0x0045B380`, `isDoorOpen` `0x0045B320`,
`getProp/getEntity/getItem` `0x0045AC80` — so each needs one short
disassembly, then the same fields located in 17.1.

# Round 3: the Cell layout

Recovered by byte-matching the unoptimised MSVC accessor bodies in **both** Beta 14
and Beta 17.1. Every offset below is byte-identical across the two builds, which is
what makes it safe to carry b14-derived semantics into 17.1. Call counts are 17.1
xrefs and are what make the two handle fields credible.

| Accessor | VA (b17.1) | Body | Callers |
|---|---|---|---|
| `Cell::getCoord` | `0x0045D1A0` | `return (Coord*)(this+0x30)` | 188 |
| `Cell::getCellId` | `0x0045D0D0` | `return **(int**)this` | 45 |
| `Cell::typeClass` | `0x0045DC50` | `return this->[0]->[0x5C] >= 2` | 33 |
| `Cell::isDoorOpen` | `0x0045DBF0` | `return this->[0x3A] != 0` | 8 |
| `Cell::getProp` | `0x0045D550` | `out = this->[0x44]` | 1357 |
| `Cell::getEntity` | `0x00463250` | `out = this->[0x48]` | 1312 |
| `Cell::itemContainer` | `0x0045D8F0` | `ecx = this+0x4C` | 547 |

## Layout

```c
struct Cell {              // >= 0x50 bytes
    /* 0x00 */ CellType*  type;         // ->[0x00] = cellID (int)
                                        // ->[0x5C] = class; >= 2 marks types
                                        //            whose look depends on state
    /* 0x30 */ int        x;            // the embedded Coord
    /* 0x34 */ int        y;
    /* 0x3A */ uint8_t    doorOpen;
    /* 0x44 */ void*      prop;         // 0 = none
    /* 0x48 */ void*      entity;       // 0 = none   (probable)
    /* 0x4C */ /* item container -- not a bare pointer, interpretation unconfirmed */
};
```

`+0x44` is confirmed as `prop` from b14's mirror, which passes the accessor's
result into `LuigiProp::load`. `+0x48` as `entity` is inference from adjacency plus
a near-identical call count, so treat it as probable until a probe confirms it.

## Cross-check that made this safe

`isDoorOpen` (`+0x3A`), `typeClass` (`CellType+0x5C`) and `getCellId` each match
*exactly once* in each binary — those bodies are unique across ~34k functions, so
the identification is not a coincidence, and they agree between b14 and 17.1.

## Implemented

`StatMind/src/cells.rs`, exposed as two MCP tools:

* **`get_map`** — walks the table, optional inclusive bounding box. Resolves
  `cellID` through the generated `CellId` table and caches per `CellType*`, so it
  costs roughly one extra read per *type* rather than per cell. Cells are
  individually heap-allocated, so the sweep is one read per occupied cell: a
  viewport is ~2k reads, a whole map tens of thousands. That is fine
  interactively and hopeless for training — the fix is the in-process reader, not
  faster mach round trips.
* **`probe_cell`** — dumps one cell's raw `0x50` bytes plus the decoded view, and
  the `CellType`'s first `0x60`. Built for calibration: `decoded.x`/`decoded.y`
  must equal the requested coordinates, or the offsets (or the column-major index)
  are wrong for the build in hand.

## The FOV field is the next unknown, and it matters

The cell table is **not** field-of-view filtered — that is exactly why it works as
a privileged channel, and exactly why it must not be handed to an agent as-is.
`cogbench.py look` currently renders ground truth: every robot on the level,
through walls. As an agent observation that is a broken benchmark, not a feature.

Nothing in the layout above is a per-cell visibility flag. `typeClass` is a
property of the *type*, not the cell. So the missing field is almost certainly a
byte near `doorOpen` at `+0x3A` — `+0x38`, `+0x39`, `+0x3B` are the obvious
candidates, and there may be separate "currently visible" and "seen before" flags,
plus possibly a sensor-detected flag distinct from both. That last one is what
proper stealth/radar modelling would hang off.

`probe_cell` exists to settle this empirically in minutes rather than by more
static analysis: stand in a lit corridor, probe a lit cell and an unlit one at the
same distance, and diff the `0x50`-byte dumps. Until that lands, treat `get_map`
as a debug and critic channel only.

# Round 4: there is no FOV byte

Visibility is not stored on the Cell at all. Re-reading b14's mirror at `0x006E92DE`,
the FOV test is a membership query against a coordinate container on a separate
global object:

```c
// b14 0x00460110 / b17.1 0x00464010
bool isVisible(this, Coord* c) {
    Coord tmp; Coord::copy(&tmp, c);
    return lookup(this + <container offset>, tmp);   // coord passed by value
}
```

| | b14 | b17.1 |
|---|---|---|
| FOV object global | `*(void**)0x00BF7210` | **`*(void**)0x00CEFC4C`** |
| visible container | `+0x78C` | **`+0x7D0`** |
| `isVisible(Coord*)` | `0x00460110` | **`0x00464010`** (26 callers) |
| lookup helper | `0x009104E0` | `0x009D0EC0` |
| sibling container | `+0x79C` | `+0x7E0` (50 callers) |
| sibling container | `+0x780` | `+0x7C4` (10 callers) |

The correspondence is trustworthy rather than guessed: every neighbouring member
accessor in that region shifts by exactly **`+0x44`** between the two builds
(`0x780→0x7C4`, `0x78C→0x7D0`, `0x79C→0x7E0`, `0x7AC→0x7F0`), i.e. the class grew
by a fixed amount ahead of this block and nothing was reordered.

`0x00CEFC4C` is the same global that appears twice under `luigiAiActive` guards
(`0x0064EC1B`, `0x0078D143`, both calling `0x009CC080` with a bool), which is
presumably LuigiAI-related FOV bookkeeping.

The `+0x7E0` container has 50 callers against `+0x7D0`'s 26, so the hotter one is
plausibly "known / remembered" and `+0x7D0` "visible right now" — worth confirming
before relying on which is which.

## It is a vector, not a tree

b14's lookup (`0x009104E0`) is a plain linear scan:

```c
for (i = 0; i < size(container); i++)
    if (equals(at(container, i), coord)) return true;
```

with `size` `0x0090BD30`, `at` `0x008F34C0`, `Coord::equals` `0x004098F0`. So the
visible set is a **contiguous array of 8-byte Coords**, not a red-black tree.

That is better than the per-cell byte this round set out to find: reading the whole
visible set out of process costs the container's three pointers plus one bulk read,
rather than a flag per cell. It also means FOV state arrives as a compact list that
can be intersected against the cell sweep directly.

## The real conclusion

Two paths now, and they point the same way.

**Out of process** is viable: read `*(void**)0x00CEFC4C`, then the container at
`+0x7D0`, then the Coord array. Two reads for the entire visible set. This is
enough to make `get_map` FOV-filterable without finding any per-cell field.

**In process is much better**, and this round is the strongest argument for it yet.
The image cannot relocate — no `.reloc`, no `DYNAMIC_BASE` — so every function
address here is a compile-time constant at runtime. From inside the process the
shim can simply *call the game's own accessors* through function pointers:

```c
typedef bool (__thiscall *IsVisibleFn)(void* self, Coord* c);
IsVisibleFn isVisible = (IsVisibleFn)0x00464010;
bool lit = isVisible(*(void**)0x00CEFC4C, &coord);
```

No container layout, no struct offsets, no per-build offset archaeology — the same
trick applies to `cellAt` (`0x009CF7D0`), `getCellId` (`0x0045D0D0`),
`getEntity` (`0x00463250`) and the rest. Every layout assumption in this document
becomes a single function address, which is far cheaper to re-verify after a
version bump than a table of member offsets.

# Round 5: first live run (Beta 17.1 under Wine, patched SDL.dll)

Everything below was observed against a running game, not inferred.

## Confirmed working

| Thing | Evidence |
|---|---|
| The one-byte flag patch | StatMind's magic scan finds `LuigiAi` at **exactly `0x00CEBFFC`**; `magic1_ok`/`magic2_ok` both true. `initialize()` ran. |
| `loadMap()` | `map_width`/`map_height` = 100/100, `map_data` = `0x0CEA1054` (allocated). |
| Map object at `0x00CFD44C` | Independently reports 100x100 and `cells_base` = `0x0CC16DB8`, matching LuigiAi. |
| Column-major index `x*height+y` | All 10,000 slots of a 100x100 map resolve to **distinct, in-range** coords, x 0..99, y 0..99. |
| `Cell+0x30/+0x34` = x/y | Every `probe_cell` returns decoded x/y equal to the requested coords. |
| Cell name resolution | `EARTH` 5444, `EARTH_EXC` 4369, `FLOOR_YRD` 186, `STAIRS_YRD` 1 — Scrapyard types, matching `location_map` = 1. |
| Read speed | 10,000 cells in **0.4 s**. The earlier "tens of thousands of reads is hopeless" caution was wrong. |
| `mapCursorIndex` | Went `-1` -> `4253` = (42,53) after one injected keypress. |
| **Mailbox v2 input** | `move_east` delivered in 2 ms, and the entity handle `0x420000` moved from (41,53) to (42,53). Keys reach the game and move the player. |
| Patched `SDL.dll` | Game launches, renders, 52 FPS. Zero exports missing vs the DLL it replaced. |

## Cell layout, corrected against raw dumps

```c
struct Cell {
    /* 0x00 */ CellType* type;      // ->[0x00] = cellID
    /* 0x04 */ int  glyph;          // ASCII! 0x2E '.', 0x23 '#', 0x3C '<'
    /* 0x08 */ int  color;          // per-type: 483 / 485 / 489
    /* 0x0C */ int  unk;            // -1 on EARTH, 1..16 scattered on floors
    /* 0x30 */ int  x;
    /* 0x34 */ int  y;
    /* 0x38 */ u8   passable;       // 1 on FLOOR/STAIRS, 0 on EARTH
    /* 0x3A */ u8   transparent;    // ditto
    /* 0x44 */ u32  prop_handle;    // 0 = none; observed 0x00440000
    /* 0x48 */ u32  entity_handle;  // 0 = none; observed 0x00420000, 0x00450001
};
```

**`Cell+0x04` is the game's own render glyph**, which is a better find than the flag
this hunt set out for: the renderer needs no cellID-to-glyph heuristic at all.

Two corrections to earlier rounds:

* **`+0x3A` is not `doorOpen`.** Carrying b14's `isDoorOpen` name into 17.1 was
  wrong. It is set on **100% of walkable cells and 0% of solid ones** (186/186
  `FLOOR_YRD`, 1/1 `STAIRS_YRD`, 0/9813 EARTH) — that is passability or
  transparency, not door state.
* **`+0x0C` is not a link id.** The first cells sampled were -1 except a stairs
  cell, which made it look like an exit link; a wider read shows 1..16 scattered
  across ordinary floor. Unidentified.

The handles at `+0x44`/`+0x48` are **not pointers** — real Wine heap pointers here
look like `0x0Cxxxxxx`, while these read `0x00420000` / `0x00450001`, i.e. a small
tag in the upper half-word. Presence testing (`!= 0`) is still correct, which is
what `get_map` relies on.

## Not working

* **`luigiAi.actionReady` never increments.** It stayed 0 across injected moves
  that visibly moved the player. This matches the static finding that `+0x08` has
  no absolute-address writer: it is not maintained in this build. The action
  handshake therefore has no turn clock and needs another source — the game's own
  turn counter, or diffing player position between reads.
* **`luigiAi.player` stays NULL.** But the player *is* visible in the cell table:
  it is the entity whose handle moves when a move is injected (`0x420000` here).
  So the player should be read from the cell table, not from `LuigiAi`.
* **The FOV container is not where round 4 predicted.** `*(void**)0x00CEFC4C +
  0x7D0` reads as an empty vector (all three pointers null) while the game is
  plainly rendering FOV, and `+0x7E0` points at string data. `+0x7C4` reads as
  `{100, 100}` — the map dimensions — so the object does own the map region, but
  the container offsets carried from b14 via the `+0x44` shift do not land.
  `0x7D0` came from b17.1's own `isVisible` disassembly, so the likely error is
  that `*(void**)0x00CEFC4C` is not that function's `this`; the "most common ecx
  before the call" heuristic picked the wrong global.

# Round 7: scanning for the rest

## Confirmed addresses (Beta 17.1, no ASLR, so these are literal)

| What | Address | How found | Verified |
|---|---|---|---|

Player record layout, isolated (16 bytes, zeros either side for at least 0x38):

```
+0x00  u32  entity handle   0x00420000
+0x04  i32  x
+0x08  i32  y
+0x0C  i32  entity id       322 == "Player"
```

## What did not work, and why it is recorded

**Structural narrowing on the HUD stats failed.** `scan_new(177)` (matter) gave
1156 candidates; requiring 300, 250 and 100 to co-occur within 256 bytes gave
**zero**. The likely reason is that the maxima are not stored: matter capacity and
energy capacity are derived from installed parts, and with 0/3 parts they come
from the core. So matter/max/core/energy are not one flat struct and cannot be
narrowed by co-occurrence.

**The turn counter is unresolved.** `scan_new(7)` -> 14021 candidates; one injected
move narrowed to 9 changed, of which three went exactly 7 -> 8 (`0x00D3C258`
static, `0x0CDD8CFC` and `0x0CDD9654` heap). But the static one then read 8 -> 7 -> 7
across two further moves, so it is not monotonic and not the counter. Left open:
turn progression can be tracked by counting injected actions instead, so this is
a convenience rather than a blocker.

**The player record has no pointer to the entity object.** A 32-word window around
it is entirely zero apart from the four fields, so integrity/matter/energy/heat
are not reachable by walking from it. They need their own scan, on a value that
can be changed on demand.

## Scanner primitives now available

`scan_new` (fresh scan for an i32), `scan_filter` (narrow to a known new value),
`scan_changed` (narrow to anything that changed, reporting new values, for when
the new value is unknown), `scan_context` (narrow by requiring several values to
co-occur within a window), `read_window` (inspect a neighbourhood). Candidates are
held server-side because a first pass on a small integer matches tens of thousands
of addresses.

## FOV: two options

Round 4's container offsets do not land, and this remains the one blocker for a
*fair* agent observation — `get_map` is ground truth and shows robots through
walls.

1. **Keep hunting the real container.** Correct, and it is the only route to
   sensor-detected-but-not-visible robots, which is what proper stealth modelling
   needs.
2. **Compute FOV harness-side** by shadowcasting from the player position over the
   cell table's `transparent` flag (`+0x3A`), which is already read and validated.
   Deterministic, fully controlled, and good enough to make the observation fair
   for terrain and line-of-sight. It would *not* reproduce sensor detection, so it
   understates what a real player sees once sensors are installed.

Option 2 is available immediately and is a reasonable interim; option 1 is the
one that ends up matching the game.

# Round 8: the stat block

## Found

```
0x0C7885D4   integrity   250     <- base+0x00
0x0C7885D8   energy       99     <- base+0x04
0x0C7885DC   matter      228     <- base+0x08
0x0C7885E0   heat          0     <- base+0x0C
0x0C7885E4   corruption    0     <- base+0x10
0x0C788590   speed        50     <- base-0x44 (reads 49/50; hedged)
```

How: `scan_new(228)` for matter gave 462 candidates; requiring the *current* core
(250) and energy (100) within 128 bytes cut that to 17; of those exactly one had
an entity-shaped neighbourhood, the rest being numeric tables or string data.

**Verified live**, which is what makes it more than a plausible-looking match:
energy read **99 -> 100 -> 99** across injected moves — regenerating between turns
and being spent on movement.

The earlier structural attempt failed because it included the *maxima* (300, 250,
100 as "x/y" pairs). Matter and energy capacity are derived from installed parts,
not stored, so requiring them to co-occur was asking for fields that do not
exist. Using only current values worked immediately.

## It is on the heap, and there is no static path

A range pointer scan over the enclosing object (`0x0C788500`-`0x0C7885E8`) found
**10** references: seven on the Wine main-thread stack (`0x0012xxxx`) and three on
the heap. No static referrer. Chaining to a stable base would take several more
rounds, each landing on another heap address, and the result would be fragile
across builds.

## Re-location instead of chaining

`find_stats(integrity, matter)` sidesteps it: both values **carry across map
transitions**, so they anchor a two-value scan whenever the address goes stale.
It scans for matter, backs up 8 bytes to the base, and keeps only records whose
integrity matches and whose heat/corruption/energy are in sane ranges.

Against the live game it returns **exactly one match**. If it ever returns more,
moving a little disambiguates: energy drifts, so a stale copy stops agreeing.

## Where this leaves the harness

Complete observation and action loop, minus FOV:

| | source |
|---|---|
| player position | static player record `0x00D2D338` |
| player stats | stat block, via `find_stats` |
| terrain + glyphs | cell table, `Cell+0x04` is the ASCII glyph |
| entities / props | cell handles `Cell+0x48` / `+0x44` |
| input | mailbox v2, ~2 ms per key |
| **field of view** | **still unsolved** |

Two of these needed value scanning rather than disassembly, and both landed in
minutes. Worth remembering as a technique: for anything the HUD displays, scanning
beats reading assembly.

And every awkward part of this round — heap addresses, no static path, offsets to
re-verify per build — is an argument for the in-process reader. From inside the
process these are calls to the game's own accessors at fixed VAs, with nothing to
maintain.

# Round 9: map transition test, and FOV declared a dead end by this route

## Heap stability: the stat block does NOT move

Snapshot across a Scrapyard -> Materials transition (`snapshot.sh`):

| | before (100x100) | after (75x75) | |
|---|---|---|---|
| stat block | `0x0C7885D4` | **`0x0C7885D4`** | **unchanged** |
| `cells_base` | `0x0CC16DB8` | `0x0CD97800` | moved |

| `fov_obj` candidate | `0x0CC16148` | `0x0463F998` | moved regions |

So the stat block can be treated as fixed within a session, with `find_stats` as a

reachable from the static map object, so that costs nothing.

Also settled: `actionReady` is still 0 *after a map load*, which is `loadMap()`
running — its last plausible chance. Dead, definitively. And the player's handle
and entity id are **per-map**: `0x00420000`/322 "Player" in the intro area became
`0x00870000`/0 "Cogmind" in the Scrapyard proper.

## FOV: everything tried, and why it failed

1. **b14's container offsets, shifted.** `*(void**)0x00CEFC4C + 0x7D0` reads as an
   empty vector on two different maps while the game is plainly rendering FOV.
   The `+0x44` neighbour-offset shift that produced `0x7D0` was derived from
   accessors that may belong to a different class.
2. **Coordinate-pair scan.** Scanning for the player's own coords found 10 pairs,
   one of which is `fov_obj+0x08` — so that object *is* view-related. But none of
   the dense coordinate arrays nearby is a FOV blob: the best (`0x045D4C28`, 23/24
   in-range) is scattered map-wide with a consecutive run, i.e. a path or wall
   segment.
3. **Vector triples inside `fov_obj`.** Seven candidates with 8-byte-divisible
   spans; the three largest contain zeros or string data.
4. **Per-cell fields.** Diffing a visible cell against a distant one of the same
   type showed differences out to `+0xB4` (the Cell is much larger than the 0x50
   originally read). All candidates fail a blob test against the player position:
   `unk_2c`, `unk_98`, `unk_a0` have hundreds of distinct values including
   pointer-shaped ones, so those offsets are inside other structures. `unk_40` has
   exactly **10** distinct values — `-9999` on 4992 cells, then 1..7 on ~80 cells
   each — which is room/zone ids, not visibility.

Conclusion: **FOV is not a per-cell flag**, consistent with b14, and locating the
container in 17.1 by these methods has not worked.

## The proposal that retires the problem

Do not look for FOV state. **Capture what the game renders.**

The shim is already inside the process and already inside SDL, which is where all
rendering goes. Hooking the surface update gives the finished screen, and the map
pane is a fixed grid of character cells. That yields:

* **exact** field of view, including partial occlusion around machinery, sensor
  blips, and every other special case -- because it is literally the player's view
  rather than a reconstruction of it;
* the message log, the parts list and the whole HUD as text, which also retires
  the stat-block hunt and the `actionReady` problem (`Time:` is on the HUD);
* immunity to struct-layout drift between builds, since glyph grids do not move.

This reframes the architecture cleanly:

| channel | source | purpose |
|---|---|---|
| actor observation | rendered SDL surface | exactly what a human sees |
| critic / privileged | cell table at `0x00CFD44C` | ground truth, FOV-independent |
| actions | mailbox v2 | ~2 ms per key |

The two channels are what the asymmetric actor-critic design wanted anyway: the
agent sees the screen, the critic sees the truth, and evaluation uses only the
former. It also means the vision track and the structured track share one
substrate instead of needing separate harnesses.

# Round 10: the blit sniffer

Cogmind re-composites the whole screen every frame instead of tracking dirty
rectangles. Every tile it draws is a blit call, so **the set of blit destinations
in a frame is the field of view** — and it is the real one, including partial
occlusion around machinery and sensor blips, because it is the render itself
rather than a model of it. The source rectangle within the atlas identifies the
glyph, so a frame yields glyph-and-position for the whole screen: map pane,
message log, parts list and HUD alike.

No hooking was needed. We compile SDL, so the blit path is instrumented directly:

* `src/statmind_blit.h` — declarations for the two entry points.
* `src/statmind_ipc.h` — the log and its functions (defined once, in SDL.c's TU).
* `src/video/SDL_surface.c` — `Statmind_RecordBlit` at the end of `SDL_UpperBlit`,
  after clipping, immediately before `SDL_LowerBlit`, so the recorded rect is what
  actually gets drawn.
* `src/video/SDL_video.c` — `Statmind_PublishFrame` at the top of `SDL_Flip` and
  `SDL_UpdateRects`.

Design notes:

* **Off by default.** `enabled` is 0 and a reader writes 1, so an unused build
  pays one load and a branch per blit.
* **Two buffers.** Blits accumulate into one while the other stays published, so a
  reader always sees a complete frame. `frame` is re-read after the data and a
  mismatch means retry.
* **`StatmindBlit` is 20 bytes, not 16.** Seven shorts then a `u32` pads to 20
  with `src_id` at `+0x10`. Verified by compiling an `offsetof` dump rather than
  reasoning about it — the natural guess is wrong.
* Log header is 40 bytes; `rects` starts at `+0x28`. Whole struct 327,720 bytes.

Rust side is `src/blit.rs` with tools `blit_status`, `blit_enable`, `blit_frame`.
The log is located by magic scan (`0xBADBEEF3` / `0x79533EDB`) once and cached.

## Why this is the right answer rather than a hack

It retires most of the outstanding unknowns at once. FOV becomes exact instead of
unfindable. `Time:` is on the HUD, so the turn counter stops mattering. The stat
block is on the HUD too, so heap addresses and `find_stats` stop mattering. And
glyph grids do not move between builds, unlike every struct offset in this
document.

It also lands the architecture where the actor-critic design wanted it:

| channel | source | purpose |
|---|---|---|
| actor observation | blit frame | exactly what a human sees |
| critic / privileged | cell table `0x00CFD44C` | ground truth, FOV-independent |
| actions | mailbox v2 | ~2 ms per key |

Evaluation uses only the first. The vision track and the structured track share
one substrate instead of needing separate harnesses.

## Round 10b: measured, and corrected

The first attempt recorded zero blits. That was a bad test, not a bad mechanism:
`total_blits` was read microseconds after enabling, before any frame boundary.

Rather than guess a second time, a **call-site census** was added
(`g_statmind_calls`, magic `0xBADBEEF4`) counting every plausible entry point.
Over ~1009 frames:

| entry point | calls | per frame |
|---|---|---|
| `SDL_FillRect` | 301,388 | ~299 |
| `SDL_LockSurface` / `Unlock` | 301,397 | ~299 |
| `SDL_UpperBlit` | 30,050 | ~30 |
| `SDL_LowerBlit` | 30,051 | ~30 |
| `SDL_UpdateRect` / `Rects` | 1,012 | 1 |
| `SDL_Flip` | 1,009 | 1 |
| `SDL_GL_SwapBuffers` | 0 | never |
| `SDL_SoftStretch` | 0 | never |

Two things follow.

**Beta 17.1 dirty-rects; it does not recomposite the screen every frame.** While
idle it redraws exactly one 12x24 cell. So a single frame is *not* the field of
view, and the log was reworked to accumulate: the reader bumps `clear_req`, acts,
waits for the redraw to settle, then reads everything drawn in between.

**`FillRect` is the dominant path.** In ASCII mode a cell is a background fill
plus a glyph blit, so both are recorded into one list with a `kind` tag — fills
carry the colour in `arg`, blits carry the source surface id, and `sx`/`sy` give
the atlas position that identifies the glyph.

### First real capture

Window spanning two injected moves:

```
count=2597   1532 fills + 1065 blits   dropped=0
every draw exactly 12x24
dx all multiples of 12, dy all multiples of 24
columns 20..136, rows 0..52, 402 distinct cells touched
```

A clean character lattice, so **the screen grid is 12x24 pixels per cell**. The
drawn-cell pattern shows a UI divider at columns 84-87 redrawing constantly, a
HUD band at rows 10-11, and a dense cluster at columns 20-56 / rows 18-32 which
is the map pane around the player.

`StatmindDraw` is 20 bytes (`dx dy w h sx sy kind pad arg`); log header 40 bytes
with the array at `+0x28`. Both verified with an `offsetof` dump, again.

### Next: calibrate screen cell -> game coordinate

The lattice is confirmed but the mapping is not. The player's game position is
known exactly from the static record, so injecting a move and correlating the
changed cells against the known delta will pin the map pane's origin and the view
offset. After that, a capture converts directly into a glyph grid in game
coordinates -- which is the field of view, exactly as the game drew it.

## Round 10c: geometry measured, screen->game mapping NOT solved

### Solid

* **Character cell is 24x24 px, drawn as two 12x24 blits.** `dx mod 24` splits
  50/50 between 0 and 12, `dy mod 24` is always 0, and **164 of 166** blit cells
  have a horizontal 12px neighbour. So screen cell = `(dx/24, dy/24)`; an earlier
  reading of "12x24 cells" was counting columns at double resolution.
* Capture works: clear, act, read. A two-move window gave 2600 draws
  (1051 blits + 1549 fills), zero dropped.
* Fill occupancy shows the panes plainly: a 2-cell-wide divider that redraws every
  frame, a HUD band, and a map cluster.

### Not solved: screen cell -> game coordinate

Three approaches failed, and the failures are informative:

1. **Glyph correlation against the cell table.** Scored offsets by how consistently
   the atlas position predicts the cell's glyph. First attempt returned score
   1.000 at a degenerate offset where all 34 atlas keys "mapped to" `#` -- every
   sampled cell had landed on wall. Adding a 1:1 term (a font atlas should be
   roughly one position per character) removed the degeneracy but produced no
   lock: best 0.96 consistency but only 3 characters across 19 keys.
2. **Weak glyph signal.** The map holds just five distinct characters
   (`#` 2975, `.` 2613, `+` 30, `<` 5, `/` 2), so glyph identity carries little
   information; it is effectively a two-tone bitmap match.
3. **Mouse warp + `mapCursorIndex`.** Should have been exact -- inject a pointer
   position, read the game's own coordinate. Two of five samples returned a
   coordinate and three returned `-1`, and the two that worked implied 150 px and
   40 px per cell against a measured 24. `mapCursorIndex` tracks the game's
   *keyboard* cursor, which follows the player, not `SDL_WarpMouse`.

### The suspicious observation

**26 distinct atlas keys mapping mostly to `.`** does not look like a font atlas,
where one character occupies one position. It looks like a tileset, or like
Cogmind's ASCII mode drawing terrain from a sprite sheet with per-type variants.
Worth confirming the render mode before investing more in glyph correlation --
if terrain has many sprites per character, that approach is unsound regardless of
the offset.

### Better next step

Do not correlate glyphs. Correlate a **known coordinate against a known redraw**:
put the game in keyboard-cursor mode, step the cursor one cell with a bound key,
and capture. `mapCursorIndex` gives the exact game coordinate and the capture
gives the exact screen cell that changed, so one or two samples pin the affine
mapping with no glyph knowledge at all. Everything needed for this is already
verified working; it just needs the cursor driven by the key bound to it rather
than by the mouse.

## Round 10d: screen <-> game mapping LOCKED

Cursor mode made this trivial, and the procedure is the one to keep.

**Method.** Put the game in keyboard-cursor mode. `blit_clear`, step the cursor one
cell with a movement key, read `LuigiAi.mapCursorIndex` (an exact game coordinate,
still live in b17.1) and read the capture. A cursor step redraws almost nothing --
70 to 184 draws over 3 screen cells -- so the busiest cell *is* the cursor's new
position. One sample pins the offset; no glyph knowledge needed.

**Result, confirmed four times:**

| step | cursor game coord | busiest screen cell | offset |
|---|---|---|---|
| east | (60,34) | col 28, row 26 | dc=-32 dr=-8 |
| north | (50,27) | col 18, row 19 | dc=-32 dr=-8 |
| southwest | (49,28) | col 17, row 20 | dc=-32 dr=-8 |
| west | (58,38) | col 26, row 30 | dc=-32 dr=-8 |

```
screen_col = game_x - 32        pixel_x = 24 * (game_x - 32)
screen_row = game_y -  8        pixel_y = 24 * (game_y -  8)
```

Exposed in `blit.rs` as `CELL_W`/`CELL_H`, `VIEW_DC`/`VIEW_DR`, `screen_to_game`
and `game_to_pixel`.

**Caveat worth stating loudly:** the offset is the *current scroll position*, not a
constant. Cogmind pans the view, so it has to be re-derived whenever the view
moves. The cursor-step procedure is cheap and reliable; the glyph correlation of
round 10c is not, and should not be revisited.

### Still outstanding: a full-repaint trigger

The mapping works, but a capture only contains what *changed*, and Beta 17.1
dirty-rects aggressively -- a cursor step redraws two map cells. So converting a
capture into a complete FOV mask needs an event that repaints the whole map pane.
Candidates: entering a map (which certainly repaints everything), or a display
toggle. Alternatively, accumulate deltas from map entry, which yields both the
explored set and the currently-visible set, and is arguably the better shape for
an incremental observation anyway.

Note also that F2 (`CMD_GAME_TOGGLE_CURSOR`, keysym 283) was sent and did not
leave cursor mode -- movement keys still drove the cursor rather than the player.
Worth understanding before relying on programmatic mode switching.

## Round 11: FOV from a full repaint, and glyph decoding ruled out

### Forcing a full repaint

Opening and closing the commands panel (F1, keysym 282) repaints the whole screen.
The trick is **where to clear**: clearing before opening overflows the 16384-entry
buffer with the panel's own text and loses the map repaint entirely (`draws=16384`,
and the player's own cell absent from the result). Clearing *between* open and
close captures only the closing repaint:

```
count=8558  dropped=0  frames=70
map cells with a glyph: 325   player drawn: True
```

Converted to game coordinates, that is a clean field of view -- a room, a corridor
running south, walls bounding it:

```
              ###########
              ..,........
        ###,,.,..........
        ##,...,..........
       ###,...,..............
       #,,...............@...
      .,.....##########...###
                    ###..
                   ,.+...
```

**So FOV is solved:** force a repaint, capture, convert with the view origin, and
the drawn map cells are what the player can see.

### Glyph decoding does not work, and here is why

The plan had been to read the character from the blit's source rect. It fails:

* `sx=336 sy=0` draws **124 `.` and 24 `#`**; `sx=72 sy=0` draws 39 `#` and 29 `.`;
  `sx=12 sy=96` draws both plus a `<`. The three dominant keys are all impure.
* Only 43 of 49 keys are pure, and consistency tops out at 0.763.
* Taking the **first** blit per cell instead of the last gives an *identical*
  result, so there is exactly one glyph blit per cell -- the impurity is not a
  layering artifact that better bookkeeping could fix.
* There are only two source surfaces, `0x03D87CF0` and `0x03D87D90`.

The explanation: those are **glyph cache surfaces with recycled slots**, not a
static font atlas. A source rect names a cache slot whose contents change over
time, so it cannot identify a character without also tracking what was rendered
into each slot. This also explains round 10c's puzzle -- 26 atlas keys "mapping
mostly to `.`" was never a coherent mapping to begin with.

### Which is fine, and arguably better

Nothing needed glyph decoding. The two channels divide cleanly:

| what | from | why that source |
|---|---|---|
| **which cells are visible** | blit *positions* + view origin | the game's own render, so occlusion and sensors are exact |
| **what is in each cell** | cell table at `0x00CFD44C` | already read and validated, with real cell ids and names |

Positions from the render, content from memory. The render answers the question
memory could not (visibility), and memory answers the question the render cannot
(identity). Neither needs the other's weakness.

## Seeds are deterministic (verified)

`worldSeed` in `options.cfg`, written before launch. Same seed twice gave an
identical map fingerprint (`6e346a4203eb37c6`); a different seed gave a different
one (`1121a3191c1a26b0`). That is the property the whole benchmark rests on.

## Fresh runs need an isolated profile, not a keystroke

`open -a Cogmind` **resumes** the save -- confirmed by the player reappearing at
the exact prior position, and by a "Resuming world seed: " string in the binary.
`CMD_GAME_NEW` (Alt+F10) does reach the game but raises a prompt that RETURN did
not answer, and guessing further at blind UI was not worth it.

The reliable route is a profile with no save file, which forces a new game.
`episode.py` creates `~/Documents/Cogmind-bench` with its own `options.cfg`,
`advanced.cfg`, `scores/` and an empty score history.

## Modifier delivery was broken, and is now fixed

Alt+F10 produced **zero draws** -- the game did not react at all. The shim was
only calling `SDL_SetModState`; Cogmind also wants the modifier's own key state,
which updates only when real key events pass through. Pressing the modifiers as
actual keys around the keystroke took Alt+F10 from **0 to 8091 draws**.

This mattered well beyond one command: **96 of the 493 bindings carry a
modifier**, so roughly a fifth of the action space was silently dead.

## Launching directly: three traps

`-customFilePath` cannot go through `open -a`, so the wrapper's wine is invoked
directly. Each of these fails in a way that does not point at its cause:

1. cwd must be the game directory (`FATAL ERROR: init | Unable to open object data`).
2. `DYLD_FALLBACK_LIBRARY_PATH` must include `Contents/Frameworks`
   (`Library not loaded: @rpath/libinotify.0.dylib`, reported against
   *wineserver*, not the game).
3. Never wrap it in `nohup` -- SIP strips `DYLD_*`, silently reintroducing (2).

## Scoring: validated against 152 real runs

`scorehistory.txt` is one row per completed run with score, deepest location,
mode and seed. Parsing it against the player's real history (152 runs, six
Cogmind versions, 15 wins) found three bugs that synthetic data would not have:

* The header is **four** lines, not one. Prefix matching passed two junk rows off
  as runs; rows are now accepted only if they parse with a version and an integer
  score -- validating beats pattern-matching when the header can grow.
* **Locations can be multi-word** (`Frmr TC4`, `Tau Ceti`; 6 of 152 rows), which
  shifts every column after them.
* The positional pass **overwrote** the right-anchored `mode`/`seed` it had just
  set -- which is why `mode` was reading as `80`/`81`/`82`.

After the fixes: every score an integer, `mode` is `['Rog']` throughout, and all
15 endings (`Fleet`, `Eridani`, `Tau Ceti`, `Frmr TC4`) parse with correct seeds.

## Open

* Detection has not watched a **live** death. The `scorehistory` branch is
  verified against real rows and against a stale-baseline trigger, but no run has
  actually ended under observation.
* `CMD_GAME_NEW`'s confirmation prompt is still unanswered, which is a UI-domain
  problem rather than an input one.

# Round 13: the descent bot -- gate test PASSED

The question was whether a competent program can get down a floor through this
action surface at all. It can: one run descended **three times**, visiting six
maps across four depths, before being killed.

```
route: -11 MAP_YRD -> -10 MAP_MAT -> -10 MAP_MIN -> -9 MAP_MAT
       -> -9 MAP_MIN -> -8 MAP_MAT
score: 2470     result: "Destroyed by H-55 Commando with Assault Rifle"
bonus: pacifist 470   (it kills nothing -- it only paths)
```

`bot.py` reads the cell table for terrain and exits, BFS-routes to the nearest
`STAIRS_*`, and steps along the path, replanning as it goes. It uses **ground
truth**, not field of view, so it is an upper bound on pathing rather than a fair
baseline; a fair one restricts to the blit-derived visible set.

## Four things blocked it, all found by running it

1. **Floor transitions invalidate the player record.** The handle drops to zero
   while the next map loads. The first version read that as death and reported a
   *successful* descent as a failure. Anything reading that record must wait out
   the transition rather than trust one sample.
2. **Confirmation prompts silently swallow movement.** `warnOnCaveinMove`
   defaults to 1, and a swallowed keystroke is indistinguishable from a wall from
   outside -- the bot deadlocked on one cell for six attempts. The profile now
   disables every warning and confirmation it can.
3. **The evolution screen blocks every descent**, and `CMD_EVOLVE_CONFIRM` does
   nothing until the evolution points have actually been spent. Pressing RETURN
   alone achieves nothing, which is what made a live run look like a death. The
   fix is to allocate (RIGHT x3) and then confirm.
4. **Walking into a hostile spends the turn attacking**, so position does not
   change and it looks like a wall. Blacklisting the cell and rerouting gets past
   it; giving up on a stuck cell does not.

## Death detection: verified against a live death

The untested branch from round 12 now has evidence. On death the watcher fired via
`scorehistory`, the row parsed correctly, and Cogmind wrote **both** score files:

```
Beta 17.1 260903  2470  -8/MAT  ... Rog COGBENCH1
new_score_files: cogbench-260903-114242-0-2470.json
                 cogbench-260903-114242-0-2470.txt
```

The seed in that row is `COGBENCH1` -- the seed set before launch carried all the
way through to the scored result.

## The JSON scoresheet is the scoring oracle

`jsonScoresheet=1` yields a 32 KB JSON per run. **Its keys are camelCase**
(`totalScore`, `runResult`, `bestStates`), *not* the snake_case of
`scoresheet.proto` -- proto field names do not transfer, and reading it with them
silently returns nulls for everything.

Useful contents: `header.runResult` (cause of death in plain English),
`performance.totalScore`, `route.entries[]` (every map with depth and type -- the
tier ladder comes straight from this), `bonus`, `bestStates` (sight range, evasion,
capacities), `lastMessages`, and a 50-line ASCII map of the run.

Note that Cogmind depths are negative and the player *ascends* toward the surface,
so progress is the **maximum** (least negative) depth. Calling the minimum
"deepest" reads as progress and is backwards.

## What the gate result actually says

The remaining blockers are **game** problems, not harness problems: no combat, no
part management, no hacking. That is the right outcome for this test -- it means
the action surface is sufficient to play, and the Lua API can now be designed
around what a bot demonstrably needed rather than around guesses.

# Round 14: calling the scoresheet writer -- the game serialises itself

The observation problem was being solved backwards. Cogmind links protobuf 3.5.1
and compiles `src/web/scoresheet.pb.cc`; it already knows how to serialise a run,
and the manual says it can do it *mid-run*: "Create a scoresheet for the current
run in progress, including most data up until this point", bound to `Alt-Shift-S`
(`CMD_BS_DEFAULT_OUTPUT_DUMP`, the only two `OUTPUT_*` commands in the 329 --
the other is `Alt-Shift-M`, Output Map). So rather than reverse-engineer state,
ask the game for it.

## 14.1 The schema, recovered from the binary

protobuf's generated code registers a schema by handing the runtime a serialised
`FileDescriptorProto`, which therefore sits verbatim in `.rdata`. It is at file
offset **0x81A080**, **77315 bytes**, anchored by `0A 14 "web/scoresheet.proto"`
(field 1, wire type 2, length 0x14 -- anchoring on the tag as well as the text
avoids the `.pb.cc` assert-path strings, of which there are ~200).

The length is not stored beside the blob (it is an immediate in the registration
call), so `harness/extract_proto.py` walks top-level fields until the bytes stop
being a valid `FileDescriptorProto`. That terminates exactly at `62 06 "proto3"`
followed by unrelated `.rdata`. Cross-checked: `protoc --decode` accepts all
77315 bytes and yields 15796 lines, and the emitted `.proto` recompiles.

```
harness/extract_proto.py -o schema/scoresheet-b17.1.proto --verify
```

package `Protobuf`, syntax proto3, **30 messages, 12 enums**. Highlights:

| message | what it carries |
|---|---|
| `Cogmind` | `coreIntegrity/matter/energy` as `{current, maximum}`, corruption, temperature, movement `{mode, speed, overweightFactor, teleportitisLevel}`, location |
| `PartSection` | `{int32 slots; repeated string parts;}` -- power/propulsion/utility/weapon **and inventory** |
| `Route.Entry` | per-map `Stats`, `discoveredExits[]` with `destination`/`destinationKnown`/`reached`, schematics, fabrications |
| `Map` | `repeated string lines` |
| `Stats` | 17 categories: build, resources, kills, combat, alert, stealth, traps, machines, hacking, bothacking, allies, intel, exploration, actions, rpglike, player2, polymind |
| `MapType` | 49 values -- the authoritative b17.1 map table (`MAP_SCR=37`, `MAP_DSF=35`, `MAP_SUB=36`, `MAP_FRG=38` are out of sequence, so they were added later) |

This supersedes both the public prerelease repo (a snapshot of some other build)
and inferring fields from a JSON sample -- proto3 omits defaults, so an absent
field is invisible in a sample but present in the schema.

## 14.2 The writer, and its two guards

`Scorekeeper::` survives as two log strings, which is all the anchor needed:
`Scorekeeper::totalScore()` at `0x00C1A394` and
**`Scorekeeper::createProtobuf()` at `0x00C1A590`**. Nearby in the same string
pool: `"dumps"` `0x00C1A34C`, `"scores"` `0x00C1A354`, `"RUN: "`, `"_log"`,
`"_combat"`, `"scorehistory.txt"`, `".json"`.

Their code xrefs land in one 40 KB function. Three functions matter:

| VA | what | callers |
|---|---|---|
| `0x00474B90` | `std::string __thiscall Scorekeeper::outputScoresheet(bool isDump)` | `0x007BFAF7` (isDump=0, run end), `0x007D6416` (isDump=1), `0x0083A4CC` (isDump=1) |
| `0x0047F450` | appends a row to `scorehistory.txt` | only `0x0047E92E` |
| `0x00480270` | `Scorekeeper::createProtobuf` -- builds the message *and* writes the `.json` | only `0x0047EA1F` |

`0x00474B90` is the single entry point: it calls the other two itself.

The ABI, from the call site at `0x007D640B`:

```
6A 01           push 1                 ; [ebp+0x0C] isDump
8D 45 D4        lea  eax,[ebp-0x2c]
50              push eax               ; [ebp+0x08] hidden return buffer
B9 58 C6 D2 00  mov  ecx,0xD2C658      ; this -- the Scorekeeper singleton
E8 75 E7 C9 FF  call 0x474B90
...
0047F424        mov eax,[ebp+8]        ; MSVC hands the buffer back out
0047F440        ret 8                  ; callee pops both arguments
```

`isDump` is not cosmetic. It gates three things, and two of them are why this is
safe to call:

* `0x00474BD0` -- skips the "no scoresheet for suicides below depth 9" gate and a
  decrement of a global at `0x00D25740`, so a dump consumes nothing.
* **`0x0047E920` -- skips the `scorehistory.txt` append entirely**:
  ```
  0047E920  movzx ecx,BYTE PTR [ebp+0xc]
  0047E924  test  ecx,ecx
  0047E926  jne   0x47E933              ; isDump -> jump over it
  0047E92E  call  0x47F450              ; ... the append
  ```
  This is the property the benchmark depends on. `episode.py` detects the end of
  a run by watching that file, so a dump that appended to it would fake a
  completed run on every call. **Verified empirically: three consecutive dumps
  left the file's md5 unchanged.**
* `0x0047E354` / `0x0047E3A5` -- output directory `dumps` instead of `scores`, so
  dumps never collide with the scoresheet `episode.py` reads at the end of a run.

## 14.3 Why call it instead of sending Alt-Shift-S

The keystroke needs no patching and remains a valid fallback, but it only fires
in `CMD_DOMAIN_BS_DEFAULT`. With a menu, an inventory pane or the evolution
screen up it does nothing -- and "did nothing" is indistinguishable from "the
dump is still being written". A direct call works in any UI state and reports its
own completion. The first successful dump of this round was taken with the
opening dialogue up, which the keybind could not have done.

## 14.4 Where the call happens

`SDL_Flip` / `SDL_UpdateRects` are the shim's only hooks on the game's own
thread, so `Statmind_PublishFrame()` now services main-thread work *ahead of* its
`enabled` early-return, and the IPC thread only ever bumps a counter. Cogmind is
single-threaded; calling the writer from the IPC thread would race every piece of
state it reads. The mailbox gains command `'D'`, whose ack means "the file is on
disk" rather than "the request was queued", bounded by `repeat` as a millisecond
budget so a minimised game cannot wedge the mailbox.

Resolution refuses to call anything unless four independent fingerprints match --
the prologue, both `movzx ...,[ebp+0xc]` sites (which pin where the bool lives
*and* that the scorehistory append is guarded by it), and the `ret 8` epilogue.
The singleton is **not** hardcoded: it is read out of the `mov ecx, imm32` at the
game's own call site, and the relative `call` there must land on the
already-fingerprinted function. Live confirmation, first try:

```
status ready   module_base 0x00400000   writer 0x00474B90   scorekeeper 0x00D2C658
```

## 14.5 A GCC inline-asm trap: `"r"` includes `%esp`

The first working version wrote the dump correctly but returned garbage. The
return buffer held `74` at `+0x0C` and `79` at `+0x10`; a valid MSVC 2010
`std::string` has size at `+0x10` and capacity at `+0x14`. A four-byte shift.

The thunk had been written as

```c
__asm__ __volatile__("pushl %[arg2]\n\t" "pushl %[arg1]\n\t" "call *%[func]\n\t"
    : "=a"(ret) : [func]"r"(fn), [arg1]"r"(a1), [arg2]"r"(a2), "c"(self) : ...);
```

and GCC, seeing the buffer at the bottom of the frame, satisfied `"r"(a1)` with
**`%esp` itself**:

```
pushl %eax        # arg2
pushl %esp        # arg1 -- esp has ALREADY moved; pushes &ret - 4
call  *%edi
```

So the callee constructed its string four bytes below the buffer. Everything
still appeared to work, because the writer's side effects do not depend on the
return value. Fix: pin operands to `esi`/`edi`/`ebx` -- the three registers a
`__thiscall` callee must preserve. Also `this` must be an in-out operand
(`"+c"`), not an input: the call destroys `ecx`, and as a plain input GCC would
go on believing `ecx` still held it.

The struct now publishes the first 32 bytes of the return buffer verbatim, so a
future build that moves the `std::string` fields can be diagnosed from a status
read instead of a rebuild.

For the record, the layout was taken from the game's own code rather than a
header: `_Tidy` at `0x009BBF20` branches on `cmp [ecx+0x14],0x10` (capacity at
`+0x14`, 16-byte buffer), and the copy constructor at `0x009AF1B0`
copy-constructs the allocator from `src + 0x18`, which puts it after both size
fields and makes the object 28 bytes.

With the fix, the writer returns **the full path of the dump it just wrote**:
`Z:\Users\heni\Documents\Cogmind-bench/dumps/cogbench-260903-134446-0-0.txt`
(74 chars, capacity 79 = 74|15 -- the MSVC growth pattern that identified the
pair in the first place). Mixed separators: the profile half carries those of the
`-customFilePath` we passed in, the rest are the game's own.

## 14.6 `map.lines` is a known-map oracle

50 rows of 50 characters, `?` for unexplored, otherwise the real glyphs --
Cogmind's own notion of what the player knows. No shadowcasting, no
partial-occlusion modelling, no glyph decoding from blits.

It is a window **centred on the player**:

```
game_x = col + player_x - 25
game_y = row + player_y - 25
```

Verified rather than assumed. With the player at (58,51), `@` sat at
(row 25, col 25) and `<` at (row 26, col 26) -> game (59,52); probing that cell
returned `STAIRS_YRD`, glyph `<`. Two east steps moved the origin from (33,26) to
(35,26) and `exits_relative_to_player` from (+1,+1) to (-1,+1). The
2:1-downsample reading of the same grid is ruled out: it would have put the
player at col 29, not col 25.

Two limits: 50x50 on maps that are 100x100, so this is a *local* view of the
known map rather than all of it; and the origin moves whenever the player does.
Edge-of-map behaviour is untested.

At 20 seconds into a seeded run, with `jsonStatDump=1`:

          runResult "(the current situation is... good)"   <- in-progress status

## 14.9 Two process traps hit this round

* **Every `cargo build` drops the code signature**, and with it the
  `com.apple.security.cs.debugger` entitlement `task_for_pid` needs. The failure
  is `Failed to get task port for PID <n>: 5`, which reads like a permissions
  problem with the *game*. Cost two debugging detours; `build-statmind.sh` now
  does both steps and verifies the entitlement survived.
* **The SDL makefile does not track the shim headers as dependencies.** Editing
  `statmind_scoresheet.h` and running `build-sdl.sh` reports "Nothing to be done"
  and silently ships the old DLL. `touch src/SDL.c` first -- it is the single
  translation unit that includes them.

## 14.10 Two things the dump closes that were listed as open

**The turn counter.** `stats.exploration.turnsPassed`, plus per-action-type
counts in `stats.actions.total` -- and the same again per map under
`route.entries[i].stats`. Verified: two east steps gave
`turnsPassed 3, actions {overall: 2, move: 2}, spacesMoved 2`. Round 4 hunted a
monotonic turn counter in memory and gave up (the candidate at `0x00D3C258` went
7->8 then 8->7), so this is the only reliable source found.

**`Alt-Shift-M` (Output Map) writes a PNG, not text.** It lands in
`screenshots-maps/` as `<SEED>_<depth>_<MapName>_mapturn_<turn>.png`, 3600x3600
RGBA -- e.g. `COGBENCH-DUMP1_-11_Scrapyard_mapturn_3.png`. So it does *not*
solve the 50x50 window limitation of `map.lines`; it is a rendered image, useful
as a vision channel and nothing else. Note the filename carries seed, depth, map
and turn.

Operational note: nothing rotates `dumps/`. Each dump is ~30 KB of text plus
~11 KB of JSON, so an agent that dumps once a turn leaves thousands of files per
run. `statdump.py prune --keep N` exists for that, and refuses to run against the
player's own profile.

# Round 15: the first agent baselines, and what they cost to get right

`harness/agent.py` runs a local model against the harness through
grammar-constrained macro-actions. `models/gemma-4-E4B_q4_0-it.gguf` (Google's
QAT 4-bit build) under `llama-server`, GBNF over the verb set.

## 15.1 The numbers, one seed (COGBENCH1)

| policy | view | score | died | maps |
|---|---|---|---|---|
| `bot.py` | ground truth | 2470 | -8/MAT | 6 |
| `agent.py --policy heuristic --cheat` | ground truth | 1500 | -9/MIN | 5 |
| `agent.py --policy heuristic` | fair (dump fog) | **200** | -10/MAT | 2 |
| `agent.py --policy model` (Gemma 4 E4B) | fair (dump fog) | **200** | -10/MAT | 2 |

Three separable facts:

* **Fog costs ~7.5x.** Same policy, same seed, only the view changes:
  1500 -> 200. This is the dominant term in the whole experiment.
* **Round 13's 2470 is not a baseline.** It read the cell table -- whole map, no
  fog, robots visible through walls. The fair baseline is **200**. Quoting 2470
  as the bar to beat overstates it by an order of magnitude.
* **The model contributes nothing over a two-line heuristic.** Not worse --
  identical: same score, same floor, same map count.

The reason the two fair runs tie is that neither policy *fights, flees or
loots*: `damageInflicted` was 7, all of it `ramming` (i.e. accidental), and both
died to the same G-34 Mercenary. A better policy has nothing to be better with
until `fire` / `flee` / `pickup` actually work. That, not model size, is the next
thing worth building.

## 15.2 Grammar-constrained decoding works, and is the Lua rehearsal

90/90 valid generations, zero parse failures, zero retries. "The model emitted
prose" is not a reachable state. **568 ms per decision** with `cache_prompt` --
the stable system text and action list go *before* the observation so the cached
prefix is maximal; putting the observation first drops caching and costs ~6 s a
call at ~120 tok/s prefill.

This is the same mechanism the Lua shell wants at a larger vocabulary, and it is
the part of today that transferred cleanly.

## 15.3 Four bugs, three of them regressions against bot.py

Worth recording because the pattern is the lesson: `agent.py` built a parallel
loop on top of `Bot` and dropped hard-won handling each time it reimplemented
something.

1. **Never send SPACE to dismiss a screen.** On a live map it is
   `CMD_SPECIALCOMMANDS_START` and *opens* the Special Commands panel; every
   later key is then interpreted in a different UI domain and silently no-ops.
   `wake()` pressed SPACE, read the resulting zeroed player record as "not
   placed yet", and pressed SPACE again -- a self-inflicted deadlock on a
   perfectly healthy run. Recovery is RETURN -> F1 -> ESC.
2. **`player.plausible == False` means "a modal panel is open", not "dead".**
   Any panel zeroes the record's handle. Treating it as death leaves the agent
   pathing from a stale position, which from outside looks like "it keeps
   bumping into things".
3. **Staged relaxation is mandatory.** Strict routing treats every robot as a
   permanent wall, so four in one corridor makes the map unroutable: measured
   live, strict returned `None` where `avoid_entities=False` returned a 5-step
   path, and **344 of 400** decisions in a control run died as "no route".
   Try strict, then entities-allowed, then blacklist-off. bot.py already did
   this.
4. **The blocked-cell blacklist needs strikes.** Never clearing it degrades
   pathing as stale entity-blocks accumulate; clearing it every decision
   livelocks on real obstacles -- a control run spent **378 of 400** decisions
   re-attempting the same cell, (21,95). One failure forgiven at the next
   decision, two makes it permanent for the floor.

## 15.4 `map.lines` is windowed, so the harness must accumulate

Round 14 called the stat dump "close to a sufficient statistic". That holds for
resources, parts and status. It does **not** hold for the map: the 50x50 window
is centred on the player and maps are 75x75 or 100x100, so an exit walked past
ten steps ago is simply absent from the next dump. A per-dump view is memoryless
in a way the player is not, and the first heuristic control proved it -- 399
explores, one descend, 609 steps, second exit never found.

Glyphs now accumulate into a per-floor dict keyed by absolute coordinate, reset
on depth change (coordinates are reused across maps), with **entities excluded**
because robots move and a remembered robot is worse than none.

This matters beyond the harness: a fixed-state recurrent policy should not be
asked to carry the map. Accumulate it outside the model, the way a player's
memory of the screen does.

## 15.5 F12 is the diagnostic

Cogmind screenshots to `<profile>/screenshots/` on F12. Reading that PNG answers
"what screen is up" in one step. Several rounds went into brute-forcing window
offsets and testing transposes against what turned out to be a **stale player
record**, when a screenshot would have shown the Special Commands panel
immediately. Glyph decoding from blits remains impossible (round 12); the
rendered PNG is the readable channel.

## 15.6 Verification notes

`map.lines` re-verified twice more against the cell table -- 143/143 cells, and
an independent origin fit scoring **1.000 on n=472** for a dump the agent wrote
itself. Mapping is `col -> x, row -> y`, origin `player - 25`.

**Round 14's original verification was weak**: it checked `<` at
(row 26, col 26) with the player at (58,51) -- a point *on the diagonal*, which
cannot distinguish the correct mapping from a transpose. Test off-diagonal
cells, or correlate the whole window.

Glyph classes, measured rather than assumed:

| glyph | cell table | routable |
|---|---|---|
| `#` | WALL_* | no |
| `"` `!` `[` `]` `=` | FLOOR_* | yes -- items lying on the floor |
| letters | FLOOR_* | yes -- robots standing on it |
| `+` `/` | DOOR_* | reads **solid**, but opens when walked into: keep routable |
| `?` | -- | unexplored |

# Round 16: three broken primitives, and the Cog-Minder join

## 16.1 fire / pickup / wait were all sending the wrong keys

Round 15's two baselines tied at 200 having dealt **7 damage, all of it
ramming**. The cause was not policy. Three of the four action primitives never
worked, and `actions.json` had the right answers the whole time:

| verb | was sending | correct | why the old one failed |
|---|---|---|---|
| `fire` | `f`, direction, RETURN | `f`, `f` | in `CMD_DOMAIN_BS_TARGETING` the letters are *cursor movement* and RETURN is `ADD_WAYPOINT` -- it placed a waypoint |
| `pickup` | `g` (GET) | `a` (GET_ATTACH) | GET leaves the part in inventory; GET_ATTACH fits it, repeating if slots are full |
| `wait` | `'5'` | KP5 = 261 | `'5'` is unbound in that domain |

One volley now yields `volleysFired 1, shotsFired 2, shotsHitRobots 2,
damageInflicted 25` (thermal 12, EM 13).

## 16.2 Targeting does not auto-close

`f` enters targeting and firing does not necessarily leave it. The first smoke
test fired **one** volley and then spent 19 of 20 decisions pressing `f` into an
open targeting panel, going nowhere at 0 steps. Every `fire` now ends with
`x` (`CMD_BS_TARGETING_CANCEL`).

This is the UI-domain gap in its most expensive form so far: a key that is
correct in one domain silently does nothing useful in another, and the harness
cannot tell.

## 16.3 A letter glyph is not a hostile

That same smoke test opened fire on an **R-06 Scavenger** -- a salvage derelict
with no armament. `FairView.entities` treats every letter as an enemy, and the
fair view carries nothing that distinguishes derelict from hostile.

Hostility is now inferred from the only unambiguous evidence available:
`stats.combat.damageTaken.overall` increasing, with a six-decision decay. That
also encodes the right policy -- *do not start fights, but fight back* -- and it
needs no entity struct.

## 16.4 The combat log is a free entity-name channel

```
Sml. Laser (50%) Hit
  R-06 Sml. Storage Unit damaged: 12
```

Bot names appear in `lastMessages` in every dump, and they join **exactly** to
`cog-minder/src/json/bots.json` (324 entries, cloned to `harness/cog-minder/`).
`harness/botdex.py` does the lookup.

| bot | class | armament | core integrity | EM resistance |
|---|---|---|---|---|
| G-34 Mercenary | Grunt | Sml. Laser | 15 | **-25** |
| R-06 Scavenger | Recycler | **none** | 15 | -25 |
| K-01 Serf | Worker | **none** | 10 | -25 |

Two facts fall straight out and both are actionable:

* **`armament: none`** means the thing cannot shoot back. That single field
  would have prevented 16.3 entirely.
* **`Electromagnetic: -25`** is *negative* resistance -- EM does extra damage.
  Every early bot carries it, and Cogmind hands you an EM Pulse Gun at the
  start. This is exactly the shape of the "emergent script" the RAG plan
  predicts, available today as a table lookup.

**Match exactly, not by regex.** A pattern loose enough to catch `K-01 Serf`
also catches `Systems online...` and `Loading variables...` -- the first version
reported both as bots.

Limitation: the log only names what you trade fire with, so this gives a floor's

struct.

## 16.5 The entity struct, and why it is worth finding

Handles decode as `(generation << 16) | slot`: the player is slot 0, and the two
robots on a fresh Scrapyard were slots 1 and 2. But:

* `0x00D2D338` is a standalone player record, **not** array element zero --
  8 KB past it contains no other handle;
* the cell carries only the handle at `+0x48`, no pointer;
* a global scan for a robot handle returns stack copies plus a heap cluster at
  `0x0C6F1xxx` on a repeating `+0x80` stride, unidentified.

Worth pursuing rather than working around, because per Plexion the per-entity
**FOV maps** are owned by that same struct -- "an integer field for each
entity's fov map", not a bitfield, which is why round 4's hunt for a per-cell
visibility flag failed. Several adjacent layers are one map per entity; the
player's is the one wanted, and combining them yields "how many entities can see
this tile", which is a different question. Any candidate layer can be validated
in one pass against the blit-derived visible set from round 12.

## 16.6 The ten scripts

`agent.py --policy scripts`: a priority list, first guard wins. The cheap test
of the retrieval thesis -- if a hash table of ten rules beats 200, a library of
situational scripts is worth building and an embedding index is an optimisation
of something already known to work.

They target the measured failure rather than clever play, and none of them need
a bot name, which is why they could land before the entity struct was found.
First smoke test after the fixes: `flee_outnumbered x12, explore x10,
fire_adjacent x2` -- it fights and flees, which neither baseline ever did.

# Round 17: encoding a player's knowledge

Rules in this round are **a player's**, given directly, not derived from data or
from play. They are recorded verbatim in intent because the point of the
exercise is to find out whether a small table of expert priorities moves the
score at all -- before building a retrieval system to hold a large one.

## 17.1 The reframe

Ten rules were given. Only two are combat tactics (camp haulers, doorway
isolation). The other eight are **build and routing**. That inverts the
priority the harness had been working to: the agent was not losing fights
because it fought badly, it was losing because it arrived at every fight naked.
Both baselines died having lost five parts and attached nothing, holding working
weapons.

Build before tactics.

## 17.2 Why it was not fighting

Not a bug -- a rule, and an overcorrection:

```python
("fire_in_range", lambda s: s["armed"] and s["can_fire"]
                            and s["under_attack"] and s["near"] <= 6, ...)
```

`under_attack` is true only when `damageTaken` increased within six decisions,
so the agent strictly returns fire and never initiates. That was added in round
16 after it emptied both guns into an R-06 Scavenger; the result is a policy
that earns the *pacifist* bonus and scores 0 kills. Initiation needs
identify-at-range, which needs the entity struct.

## 17.3 Build rules (`harness/itemdex.py`)

`items.json` carries `Slot`, `Type`, `Damage Type`, `Support`, `Mass`, `Rating`,
`Range`, `Coverage`. Four rules encoded:

| rule | reasoning |
|---|---|
| `treads_in_materials` | MAT is dense salvage over a short walk, so capacity beats speed; treads carry the most mass per slot (`Support 20` on Lgt. Treads) |
| `biggest_storage` | inventory capacity is what lets a run leave MAT stronger than it arrived; overweight costs speed, the cheapest thing to spend there |
| `stack_damage_type` | mixed damage splits every resistance calculation; Kinetic is the default because ballistic guns are the commonest early drop |
| `pocket_launcher` | a launcher is a moment, not a loadout -- equip to break a swarm, then stow |

**The name join is the trap.** The stat dump reports `Light Treads`;
`items.json` keys on `Lgt. Treads` and carries the expanded form as a separate
**`Full Name`** field. The first version indexed on `Name` only and fired
**zero** times with a full inventory sitting there -- a join that silently
matches nothing is indistinguishable from a rule that does not apply. Index
both: 1343 items -> 2004 keys.

Equipping: `CMD_INVENTORY_EQUIP<n>` is **Ctrl+digit** (`mods=64`), and Cogmind
numbers the inventory 1..9 then 0, so list index 9 is the `0` key.

Live check on a run that had stripped itself to nothing:
`stack_damage_type -> Light Assault Rifle (Kinetic)`, then
`treads_in_materials -> Light Treads`. Correct rules, correct order.

## 17.4 Doorway funnelling

> fight in diagonals adjacent to a door to isolate enemies to 1 vs 1 in
> doorways and line them up as they rarely hop (they sometimes do tho)

A doorway admits one robot at a time, and standing on the *diagonal* rather
than in line means the queue behind cannot shoot past the one in front. It is
the cheapest way for an under-built Cogmind to turn 3-on-1 into three 1-on-1s.

Doors are already visible as `+` / `/` in `map.lines`, so
`FairView.doorway_posts()` returns the four diagonal neighbours of each known
door, nearest first. `fight_doorway` sits **above** `flee_outnumbered`: fleeing
in the open from three hostiles is being shot in the back by three hostiles.
Once posted it holds -- stepping off is what breaks the funnel.

Verified synthetically (a fresh Scrapyard has ~129 cells explored and no doors
yet, so the live map could not exercise it): door at (5,5), player at (5,8) ->
posts `[(6,6), (4,6), (6,4), (4,4)]`, nearest first.

The "they sometimes hop" case is **unmodelled**, deliberately -- better to see
it fail in a run than to guess at the frequency now.

## 17.5 Hacking (`harness/hackdex.py`)

`machine_hacks.json`: 7 machine types, 87 Terminal hacks, each with a base
chance. The given order:

```
depth -11              Layout(Zone) 50, Analysis(Swarmer) 54, Analysis(Grunt) 54
depth  -9 with traps   Traps(Reprogram) 30, Traps(Disarm) 45, Layout(Zone) 50,
                       analyses, Enumerate(Transport) 50
depth  -7              Access(Branch) 30 first, then the rest
```

Two points where the ordering deliberately contradicts the odds, and both are
the interesting part:

* **`Traps(Locate)` is the likeliest to land (60%) and is worth nothing** --
  knowing where a trap is does not stop it hurting you. `Traps(Disarm)` (45%)
  removes it; `Traps(Reprogram)` (30%) turns it on your pursuers. Sorting this
  menu by success rate picks the useless one.
* **`Access(Branch)` is promoted to first from -7 up** despite being only 30%,
  because a missed branch can lock out permanently while the other hacks stay
  available.

It returns a **plan**, not a single hack: a terminal is not one-shot, you keep
going until traced, so what matters is the order the attempts are spent in. The
first version returned one hack and `Layout(Zone)` shadowed everything below it
forever.

`Analysis` odds fall 6 points per bot tier (54% at tier 1, 0% at tier 10), and
botdex carries `Tier` -- so the two tables join: knowing what you are fighting
tells you whether analysing it is even possible.

**Not implemented: driving the terminal.** `CMD_DOMAIN_HACK` exposes only
navigation (scroll, page, home/end, close, F2 cursor toggle), so hacks are
selected by typing their name, and this harness has never driven a terminal.
`LuigiAi.machineHacking` going non-NULL is the one UI domain we can positively
detect, which makes hacking the right place to start on domain tracking.

## 17.6 Still blocked on the entity struct

it is a Hauler before engaging) and **not shooting derelicts** (the same
